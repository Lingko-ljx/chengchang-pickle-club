# 匹克球预约核心系统设计

- 日期：2026-08-04
- 状态：已由用户批准
- 阶段：第一阶段——独立预约主体

## 1. 目标

在不依赖微信、在线支付或 Formspree 的情况下，建立可以独立运行的预约闭环：用户查看真实余位并提交预约，系统为 11 片场地自动分配库存，工作人员在手机后台确认、改期或取消，用户凭预约编号查询并处理结果。

第一阶段完成并验收后，微信只作为入口、身份绑定和通知适配层接入，不改变预约核心规则。

## 2. 与现有设计的关系

本设计取代 `2026-07-30-compatible-booking-design.md` 中将 Formspree 作为正式预约提交端点的方案。Formspree 不再承担正式预约的数据存储、库存分配或状态管理。

旧设计中已经验证的兼容性原则继续保留：

- 公开介绍页保持服务端生成和脚本轻量化；
- 预约页在 HTML 层提供可见表单和明确错误状态；
- 公开交互脚本采用兼容 Android WebView 的构建目标，不依赖 Next/React 水合才能显示主体内容；
- 管理后台与公开介绍页分离，避免后台代码影响公开网站的加载稳定性。

## 3. 第一阶段范围

### 3.1 包含

- 用户预约页；
- 预约结果页；
- 预约状态查询页；
- 工作人员登录与移动端管理后台；
- 11 片场地的可用性与库存管理；
- 包场和散客两种预约模式；
- 固定 60 分钟场次及开放时段配置；
- 人工确认、改期、取消和完结；
- 操作审计；
- 邮件备用通知；
- 浏览器兼容、并发分配和安全测试。

### 3.2 不包含

- 微信公众号菜单、OAuth、OpenID 或微信消息；
- 企业微信通知；
- 小程序；
- 在线定金、全款、退款或对账；
- 会员、积分、优惠券和营销；
- 自动取消未满 4 人的散客场。

## 4. 角色与权限

### 4.1 预约用户

无需注册账号。用户可以：

- 查看可预约日期、时段和模式；
- 创建包场或散客预约；
- 获取预约编号；
- 使用预约编号与预留手机号查询状态；
- 接受或拒绝工作人员提出的改期；
- 在场次开始前取消预约；场次开始后只能由工作人员处理。

用户只能访问自己的预约，不得看到其他预约人的姓名、手机号或人数。

### 4.2 工作人员

工作人员通过独立后台登录。首版使用 CloudBase 身份认证和管理员角色白名单；初始管理员在部署时安全配置，凭据不得写入仓库。工作人员可以：

- 查看 11 片场地的日历和实时占用；
- 查看、筛选和搜索预约；
- 确认、改期、取消、完结预约；
- 调整系统分配的场地；
- 配置营业日、60 分钟开放时段和临时停场；
- 导出预约记录；
- 查看操作日志。

## 5. 用户体验

### 5.1 预约页

用户依次选择：

1. 日期；
2. 固定 60 分钟时段；
3. “包场”或“散客”；
4. 人数；
5. 姓名、手机号、可选邮箱和可选备注；
6. 隐私与联系授权。

人数限制：

- 包场：1–8 人，整片场地独占；
- 散客：一次预约 1–4 人，同一组人员不得拆分到不同场地；
- 5 人及以上的用户选择散客时，页面提示改选包场。

页面只展示仍有可分配库存的选项。显示的余位只用于帮助选择，最终分配以服务端事务结果为准。

### 5.2 提交结果页

服务端确认写入成功后，页面才显示成功，并提供：

- 随机且不可顺序猜测的预约编号；
- 当前状态“待工作人员确认”；
- 日期、时段、模式和人数摘要；
- 状态查询入口；
- “提交成功不等于已确认”的明确说明。

### 5.3 状态查询页

用户输入预约编号与完整预留手机号。验证成功后显示脱敏信息、状态历史以及允许的操作。

状态包括：

- `pending`：待工作人员确认；
- `confirmed`：已确认；
- `reschedule_proposed`：工作人员提出改期，等待用户接受或拒绝；
- `cancelled`：已取消，并记录取消方和原因；
- `completed`：已完成。

工作人员提出改期时，系统同时保留原场地并预留新场地，避免用户接受后新时段已经被占用。用户接受后进入 `confirmed`，释放原场地并使用新场地；用户拒绝后释放新场地，并恢复提出改期前的 `pending` 或 `confirmed` 状态。第一阶段不因等待确认而自动取消预约。

### 5.4 管理后台

后台优先适配手机，并提供：

- 今日待办；
- 日历视图；
- 11 片场地占用矩阵；
- 按状态、日期、模式和手机号筛选；
- 单条预约详情和操作时间线；
- 确认、提出改期、取消、完结、调整场地；
- 开放时段与停场配置；
- CSV 导出。

## 6. 场地和库存规则

### 6.1 基础模型

- 场地总数为 11 片，初始编号为 1–11；
- 每个场次固定 60 分钟；
- 每片场地在同一场次只能处于空闲、包场或散客拼场三种模式之一；
- 每个散客场的容量为 4 人；
- 散客场不足 4 人也正常开场，不设置成团门槛。

### 6.2 包场分配

包场只能占用完全空闲的场地。分配成功后，整片场地被该预约锁定；同一场次不再接受其他包场或散客进入该场地。

### 6.3 散客分配

系统采用“最满且仍能容纳整组”的优先规则：

1. 查找已有散客且剩余容量足以容纳整组的场地；
2. 优先选择已占人数最多的场地，以尽量补满；
3. 没有合适场地时，启用一片完全空闲的场地；
4. 一组散客不得拆分到两片场地；
5. 没有可容纳整组的场地时返回已满，不创建预约。

### 6.4 待确认占位

`pending`、`confirmed` 和 `reschedule_proposed` 状态均占用库存。提出改期时，原分配继续占用，新分配也被临时预留；接受改期释放原分配，拒绝改期释放新分配。取消预约释放该预约的全部分配。第一阶段不设置自动过期，避免工作人员尚未处理时预约无提示消失。

### 6.5 并发一致性

创建、改期、取消和人工调整必须在服务端事务或等价的条件写入中执行：

- 包场从空闲场地中原子选取并锁定；
- 散客人数以条件更新增加，更新后不得超过 4；
- 请求携带幂等键，重复提交返回同一结果；
- 事务冲突时重新读取一次最新库存并重试；
- 重试后仍无库存则返回明确的“该时段已满”。

## 7. 系统架构

系统拆分为五个边界清晰的单元：

1. **公开网站**：继续提供品牌、场地、人员、荣誉和联系方式；
2. **预约客户端**：负责预约、结果与查询，不自行判断最终库存；
3. **预约 API 与分配引擎**：校验输入、执行事务、管理状态迁移；
4. **管理后台**：仅通过受保护的管理 API 操作业务数据；
5. **通知适配器**：第一阶段实现邮件，未来在同一事件出口增加微信公众号或企业微信。

公开预约客户端通过版本化 HTTPS JSON API 通信，不依赖 CloudBase 浏览器 SDK。网络层提供兼容旧 Android WebView 的 XHR 实现，并可在新浏览器使用 `fetch`；页面主体不依赖 JavaScript 才能渲染。

后端采用腾讯云 CloudBase：

- 文档型数据库保存业务记录；
- 云函数提供公开和管理 API；
- 身份认证保护管理后台；
- 环境变量或密钥管理保存邮件服务凭据和通知邮箱。

现有 GitHub Pages 继续承载公开网站和第一阶段预览。CloudBase 使用独立的测试与生产环境；测试地址不视为最终生产发布。正式对外运营和第二阶段微信接入前，再绑定稳定 HTTPS 独立域名并完成需要的备案或平台校验。

## 8. 数据模型

### 8.1 `courts`

保存场地编号、显示名称、启用状态和临时停用原因。

### 8.2 `session_templates`

保存星期、开始时间、固定时长 60 分钟和是否开放，用于生成可预约场次。

### 8.3 `sessions`

保存具体日期、开始与结束时间、开放状态及特殊关闭原因。

### 8.4 `court_allocations`

每个场次与每片场地一条记录，保存模式、占用人数、包场预约标识和乐观锁版本号。

### 8.5 `bookings`

保存随机预约编号、模式、人数、姓名、标准化手机号、可选邮箱、原分配、改期提案分配、改期前状态、当前状态、幂等键和时间戳。

### 8.6 `audit_logs`

保存预约状态变化、场地调整、操作人、时间和原因。日志只追加，不由普通后台操作覆盖。

### 8.7 `notification_outbox`

保存待发送、已发送和失败的邮件事件。通知失败可重试，但不得回滚已经成功的预约业务操作。

## 9. API 行为

公开 API 仅提供：

- 查询可用日期与时段；
- 创建预约；
- 使用预约编号与手机号查询；
- 接受或拒绝改期；
- 在场次开始前由用户取消。

管理 API 仅向已认证且具有管理员角色的账号开放。所有写操作必须进行输入校验、权限校验、状态迁移校验和审计记录。

公开响应不得返回其他用户信息、内部数据库标识、邮件凭据或完整操作日志。

## 10. 邮件备用通知

以下事件写入通知发件箱：

- 新预约提交；
- 工作人员确认；
- 提出改期；
- 用户接受或拒绝改期；
- 预约取消。

工作人员通知邮箱和邮件服务凭据通过部署配置提供，不写入公开仓库。邮件发送失败只标记并重试；用户始终可以通过状态查询页完成流程。

新预约始终向工作人员配置邮箱发送提醒。用户填写可选邮箱时，状态变化也向该邮箱发送副本；未填写邮箱时不影响预约和查询。

## 11. 错误处理与安全

- 服务端未返回成功前，客户端不得显示预约成功；
- 网络中断后允许使用同一幂等键安全重试；
- 库存冲突时刷新可用性并提供其他时段；
- 查询接口按 IP、预约编号和手机号进行速率限制；
- 创建接口使用限流、蜜罐字段和服务端输入校验抑制自动化垃圾提交；
- 预约编号使用高熵随机值，不使用自增序号；
- 查询结果中的手机号和姓名脱敏；
- 表单包含隐私授权，并只收集完成预约所需的信息；
- 已完成或取消预约的个人信息默认保留 180 天，管理员可提前删除；审计记录保留不含敏感明文的业务摘要；
- 管理操作要求认证、角色授权和服务端审计；
- 日志不得记录完整手机号、邮件服务密钥或认证令牌。

## 12. 测试与验收

### 12.1 业务规则

- 同一场次 11 个包场成功，第 12 个返回已满；
- 同一场次 44 个单人散客按 4 人一场填满 11 片场地，第 45 个返回已满；
- 散客优先补入未满场地；
- 1–3 人的散客场可正常确认和完成；
- 已有散客的场地不能被包场；
- 整组散客不会被拆分；
- 取消和成功改期后正确释放原库存。

### 12.2 并发与幂等

- 多个请求竞争最后一片场地时只有一个成功；
- 多个散客请求同时补最后几个名额时总人数不超过 4；
- 用户重复点击或网络重试只创建一条预约；
- 管理员同时调整同一预约时，旧版本操作被拒绝并提示刷新。

### 12.3 权限与隐私

- 未登录用户不能访问管理 API；
- 普通用户不能枚举或查询他人预约；
- 错误响应不泄露个人信息或内部实现；
- 操作日志能追溯每次状态和场地变化。

### 12.4 浏览器与体验

- 安卓系统浏览器及常见内嵌 WebView；
- iPhone Safari；
- 微信内浏览器；
- Chrome、Edge 和 Safari 桌面版；
- 慢速网络、离线重试和 API 暂时不可用；
- 公开介绍页在预约 API 故障时仍能正常打开；
- 预约页失败时显示可理解的错误，不出现白屏或虚假成功。

## 13. 第一阶段完成标准

只有在以下条件全部满足后，第一阶段才视为完成：

1. 用户可以从公开网站完成包场或散客预约；
2. 预约真实写入数据库并正确占用 11 片场地库存；
3. 工作人员可以在手机后台完成确认、改期、取消和完结；
4. 用户可以凭预约编号与手机号查询并处理改期；
5. 并发、权限、兼容性和失败场景通过测试；
6. 整个闭环不依赖微信或在线支付；
7. 测试数据与生产数据隔离，生产密钥未进入仓库。

第一阶段验收通过后，第二阶段再设计和实现微信公众号入口、OpenID 绑定、用户微信通知及工作人员企业微信提醒。
